# Spec 10 — CRM (PRD §4.1–4.3, 4.5)

The first CRM spec. Spec 09 ended with a working evaluation loop and a
`preference_log` of what the user likes; this spec gives the user somewhere
to keep the people they meet along the way — a friend's name, contact info,
where and through which community they met, and a running tally of how often
they've stayed in touch — and a plain way to compose a message to one of
them that the user's own phone actually sends. PRD §4.4/4.6 (weekly invite
suggestions, group invites) and any automatic "who to invite to what" belong
to spec 11, not here.

No addendum exists for spec 10 as of drafting. **`docs/specs/10-crm-addition-note.md`**
(the viral/k-factor loop: a shareable event page, one-tap account creation,
share-sheet invite scripts, "N friends going" social proof) is a holding
note, not an addendum — it is read below and deliberately deferred, not
folded in; see Decisions and Out of scope for why.

---

## What is already built (do not rebuild)

- **The `contacts`, `interactions` and `invite_suggestions` tables**, their
  three enums (`interaction_kind`, `invite_suggestion_status`,
  `record_status`) and their RLS, all from spec 01's original 15-table
  migration (`supabase/migrations/0001_enums.sql`,
  `0002_tables.sql` lines 240–298, RLS generated by `0003_rls.sql`).
  `contacts` is select/insert/update only — **no delete policy** — and
  carries its own `record_status` (`active`/`archived`) for exactly this
  reason. `interactions` and `invite_suggestions` do have delete grants in
  RLS, but nothing in this spec deletes a row of either; see Decisions.
  **No new migration is needed for this spec.**
- **The Zod schemas**, in full, in `lib/schemas/crm.ts`: `contactRow` /
  `contactInsert` / `contactUpdate`, `interactionRow` / `interactionInsert`
  (no update variant — `interactions` has no `updated_at`), and
  `inviteSuggestionRow` / `inviteSuggestionInsert` / `inviteSuggestionUpdate`.
  Already re-exported from `lib/schemas/index.ts` and already covered by
  `tests/schemas.test.ts`'s generic table/enum round-trip. **Do not add a
  second schema file for these tables.**
- **The `/people` route and its nav entry.** `app/(app)/nav-items.ts` already
  lists "People" → `/people`. `app/(app)/people/page.tsx` is currently
  `<Placeholder name="People" spec="10" />` — this spec builds inside that
  same directory and keeps the "People" label; it does not rename the route
  or add a second one.
- **The five-file route shape** (`docs/CONVENTIONS.md#page-layout`):
  `page.tsx` (thin server component, gate, hand-off), `data.ts` (reads,
  server-only), `actions.ts` (`"use server"`, async functions only),
  `view.ts` (pure helpers, no directive), one `"use client"` component per
  file. `app/(app)/communities/` and `app/(app)/evaluations/` are the models
  to copy, including their `Gate` helper and `ActionResult` shape
  (`{ ok: true; note?: string } | { ok: false; error: string }`).
- **`lib/onboarding.ts`**: `ONBOARDING_STATES` ends at `activities_selected`,
  and `hasSelectedActivities(state)` already exists — every built page past
  onboarding (`/communities`, `/feed`, `/calendar`, `/evaluations`) gates on
  it. No new onboarding state exists or is needed for this spec.
- **`app/(app)/feed/data.ts`**'s `readEvents`, `readCommunitiesById`,
  `readSelections` and `occurrenceKey` — already exported, already the read
  layer `app/(app)/evaluations/data.ts` imports directly rather than
  querying the same tables again. This spec's "which event did I meet this
  person at" dropdown is built the same way: import and filter, not a new
  query against `events`/`selections`.
- **`app/(app)/communities/data.ts`**'s `readCommunities` (already returns
  every community with `id`/`name`/`status`) — reused as the "which
  community" dropdown's data source.
- **`app/(app)/communities/actions.ts`**'s `updateCommunity` — the per-field
  patch shape (`Record` of optional fields, only the ones present get
  written, `communityStatus.parse`/similar validation per field) is the
  model `updateContact` (item 2) copies exactly.
- **`lib/scraping/ics.ts`** — the hand-rolled, line-unfolding RFC 5545 parser
  spec 06 already wrote, with no new dependency. Item 5's vCard/CSV parsers
  follow the same shape and the same "hand-roll a simple text format rather
  than add a library" precedent.
- **The `invite_suggestion` LLM component** (`lib/llm/components/invite-suggestion.ts`)
  is a registered stub with a placeholder prompt, its real prompt and
  wiring explicitly deferred (per its own comment) to spec 11. This spec
  calls no LLM component at all — see Decisions.

## Scope

### 1. `/people` reads and the gated page

`app/(app)/people/data.ts` (directive-free reasons identical to
`communities/data.ts`'s and `feed/data.ts`'s own banner comments — `page.tsx`
is a server component, `actions.ts` is `"use server"` and may only export
async functions, so shared reads cannot live there):

- `readContacts(supabase, userId): ContactCard[]` — every contact the user
  owns (active and archived both — the page partitions them, per item 2),
  with `met_at_community_id`/`met_at_event_id` resolved to a display name via
  a join against `readCommunities`/`readEvents`+`readCommunitiesById`.
- `readInteractionsByContact(supabase, userId): Map<string, InteractionRow[]>`
  — every interaction row, newest first, grouped by `contact_id`.
- `readMeetableEvents(supabase, userId): { eventId, title, communityName, startsAt }[]`
  — built from `readEvents` + `readCommunitiesById` + `readSelections`
  (all imported from `../feed/data`), filtered to occurrences whose
  selection status is `'attended'`. This is both the "met at" dropdown's
  event option list (item 2) and the optional event reference on a manual
  interaction log (item 3) — one list, two forms.
- `loadPeopleData(supabase, userId)` — combines the above plus
  `readCommunities` (from `../communities/data`, for the "met at community"
  dropdown) into one `PeopleData` the page renders from.

`app/(app)/people/page.tsx` replaces the placeholder: gated on
`hasSelectedActivities` (same reasoning every other post-onboarding page
already uses — a "met at" dropdown with nothing to show, because no
activity/community/event exists yet, would be a worse gate than reusing the
one already there), with the same `Gate` helper shape as
`communities/page.tsx`, linking to `/activities` when ungated.

Low tier (`docs/CONVENTIONS.md#pure-core-server-edge`-shaped reads and page
wiring; no writes yet).

### 2. Add, edit and archive a contact

`app/(app)/people/actions.ts`:

- `createContact(input)` — validates against `contactInsert` (already in
  `lib/schemas/crm.ts`), inserts the `contacts` row, and in the same call
  inserts exactly one `interactions` row: `kind: 'met'`,
  `occurred_at: met_on ?? now()`, `event_id: met_at_event_id ?? null`. A
  contact is never created without its own founding interaction — see
  Decisions for why this is not optional.
- `updateContact(contactId, patch)` — a per-field patch mirroring
  `updateCommunity`'s exact shape: `{ name?, phone?, email?, notes?,
  met_at_community_id?, met_at_event_id?, met_on?, status? }`, only the
  provided fields validated and written. `status: 'archived'` is how a
  contact leaves the active list (`docs/CONVENTIONS.md#status-over-delete`
  — RLS grants `contacts` no delete, so there is no other way); `status:
  'active'` restores it. No other field is ever silently touched by an
  unrelated edit.
- The People page: an "Add contact" form (name required, everything else
  optional, per the schema), a card per contact showing name/phone/email/
  met-at/notes with inline per-field editing (autosave onBlur/onChange,
  the same pattern `communities-view.tsx` already uses, including a "✓
  Saved" badge per `docs/CONVENTIONS.md`'s established Community-card
  precedent), and an Active/Archived split (`partitionByArchived`-shaped —
  a small local equivalent in `people/view.ts`, not an import of
  `communities/view.ts`'s version, since every route's `view.ts` stays
  self-contained per the existing convention) with a Restore control on an
  archived card.

Medium tier per `CLAUDE.md` (server actions writing app rows).

### 3. Interaction logging and tallies

`app/(app)/people/actions.ts`:

- `logInteraction(contactId, { kind, occurredAt?, eventId? })` — `kind` is
  restricted to `'text' | 'invite' | 'hangout'` in this action's own input
  schema (not the full `interaction_kind` enum): `'met'` is written exactly
  once, by `createContact` in item 2, and letting it be logged again here
  would double-count a relationship's founding interaction in the tally.
  `eventId`, when given, is validated against `readMeetableEvents`'s list
  (item 1) — the same reused read, not a second query.

`app/(app)/people/data.ts`'s `readInteractionsByContact` (item 1) plus a new
pure `tally(interactions): { total: number; byKind: Record<InteractionKind, number> }`
in `people/view.ts` — counted live on every read, **never stored as a
counter**, which is the exact rule the `interactions` table's own migration
comment already states ("Tallies (PRD 4.5) are derived from these rows,
never stored as a counter") and this item simply honors in code
(`docs/CONVENTIONS.md#idempotent-writes`'s spirit: derive, don't cache a
fact the underlying rows already answer).

The People list shows each contact's total tally and most recent
interaction date; the contact detail view shows full interaction history
(kind, date, event if any) and a "Log interaction" form (kind selector,
date defaulting to now, optional event picker from `readMeetableEvents`).

Medium tier (writes real app rows).

### 4. Compose and send via phone

A "Message" panel on the contact detail view: a plain `<textarea>`
pre-filled with a small, non-LLM template (`"Hey {name}, ..."` — literally
that, no model call). PRD §4.2 asks for a message "composed in the CRM,"
and no LLM component appears anywhere in `docs/ARCHITECTURE.md`'s
component→gateway table for this; inventing one here would be exactly the
feature-not-in-PRD/CONVENTIONS creep `CLAUDE.md` forbids. A real drafted
invite message is `invite_suggestion`'s job once its real prompt lands in
spec 11.

Two links, shown when the corresponding field is on file:

- `sms:{phone}?&body={encodeURIComponent(text)}` when `phone` is set.
- `mailto:{email}?subject=...&body={encodeURIComponent(text)}` when `email`
  is set.

Clicking either opens the phone's own Messages/Mail app with the drafted
text already in the body — **CLAUDE.md's hard rule**: "never send a
message/text to a contact automatically; the app only prepares, the user
sends." Nothing in this app ever calls a send API.

Beneath the links, a manual "✓ I sent this" button calls `logInteraction`
(item 3) with `kind: 'text'` (the enum has no separate "email" kind, and a
sent message is a sent message either way) at the moment it is clicked —
the app has no way to detect whether the native app was actually used to
send, so this is an honest, user-confirmed log entry, not an inferred one.

Low tier (UI and a template string, wired to item 3's already-decided
action — no new server logic).

### 5. vCard / CSV parsers

`lib/crm/import.ts` — pure, no Supabase client, no `fetch`, no
`process.env` (`docs/CONVENTIONS.md#pure-core-server-edge`), mirroring
`lib/scraping/ics.ts`'s "hand-roll a small, well-known text format" call:

- `parseVCard(text): { contacts: ParsedContact[]; warnings: string[] }` —
  reads vCard 3.0/4.0 `BEGIN:VCARD`/`END:VCARD` blocks, unfolding
  continuation lines the same way `ics.ts` already does. Reads `FN` (name),
  the first `TEL` value, the first `EMAIL` value, `NOTE`, and `UID` (mapped
  to `phone_contact_id` — the one field `lib/schemas/crm.ts` already has
  for exactly this, per its own comment: "Identifier from the phone's
  address book, when imported"). A block with no `FN` is skipped with a
  warning naming its position, never silently dropped and never guessed at.
- `parseCsv(text): { contacts: ParsedContact[]; warnings: string[] }` — a
  header row matched case-insensitively for `name` (required — a missing
  `name` column is a parse error surfaced up front, not a guess),
  `phone`, `email`, `notes` (all optional); unrecognized columns are
  ignored, a data row with a blank name is skipped with a warning naming
  its line number.
- `ParsedContact = { name: string; phone: string | null; email: string | null;
  notes: string | null; phoneContactId: string | null }`.

Tests (`tests/crm-import.test.ts`, red before green,
`docs/CONVENTIONS.md#tests`): a valid multi-contact vCard, a valid CSV, a
vCard with one malformed/no-`FN` block among valid ones (both parsed and
the warning present), a CSV missing the `name` column (rejected up front),
folded/continuation-line unfolding, and a `UID` mapped to `phoneContactId`.

Low tier (pure parsing, no writes, no UI yet).

### 6. Import preview and write

`app/(app)/people/actions.ts`:

- `previewImport(text, format)` — parses only (calling item 5's functions),
  writes nothing (per `CLAUDE.md`: build the no-write path first, same
  discipline as `scripts/discover.ts --dry-run`). Also flags a likely
  duplicate against the caller's existing contacts, matching by
  `lower(btrim(name))` — the same shape `communities_user_name_key`/
  `nameKey` already establish — so the review screen can warn without
  silently skipping or silently double-adding.
- `importContacts(rows)` — takes the checked rows from the review screen
  and calls `createContact` (item 2) once per row, the same write path, not
  a second implementation. `met_on` is left `null` for every imported
  contact: the import has no real meeting date, and `CLAUDE.md` forbids
  inventing one. The founding `interactions` row (from `createContact`)
  still gets `occurred_at: now()` — "now, when this was recorded" is the
  honest fact available, not a guess about the past.

The People page gets a file `<input>` accepting `.vcf`/`.csv`; the client
reads the file to text (`FileReader`, a plain browser API, no new
dependency) and passes the raw text plus the detected format to
`previewImport`. The review screen lists every parsed row with a
default-checked checkbox, shows every warning, flags likely duplicates, and
only calls `importContacts` on confirm.

Low tier for `previewImport` (parses, does not write); Medium tier for
`importContacts` (writes app rows).

### 7. Recall and search

A plain client-side text filter on the People list — `loadPeopleData`
already reads every contact once, so this needs no new server round trip.
`people/view.ts` gets a pure `matchesQuery(contact, query): boolean`
(matches name, phone, email, notes, met-at community/event name,
case-insensitive), tested directly in `tests/people-view.test.ts`.

Low tier.

## Decisions made while drafting (do not re-litigate)

- **The viral-loop addition note is deliberately not folded in.** The note
  itself says a spec that ignores it is not wrong, and explicitly asks for
  it to be flagged to a human planning session rather than pasted in as a
  raw note — there is no live planning chat in the autonomous loop this
  spec is drafted under, so the honest way to "flag it" is to write the
  decision down here, in the open, for the review gate to see, rather than
  either building an unreviewed shareable-account-creation surface
  unilaterally or silently dropping the note. It needs its own scoping pass
  (an unauthenticated page, a new account-creation path, and a "friends
  going" social feature all raise questions — data exposure to a
  non-account visitor, what "N friends" reveals about a private list — this
  spec's own author should not decide alone). Out of scope, explicitly,
  below.
- **No new migration.** Every table, enum and RLS policy this spec needs
  already exists from spec 01. This is the first CRM-touching spec and
  still needs nothing at the schema layer — confirmed by reading
  `supabase/migrations/0001`–`0003` directly rather than assuming.
- **`/people` gates on `hasSelectedActivities`, not a new state.** Every
  built page past onboarding already gates there, and this page's own
  dropdowns (met-at community, met-at event) have nothing to show before
  that point anyway. Adding a dedicated CRM onboarding state would gate on
  a distinction the data itself doesn't need.
- **A contact always gets a founding `'met'` interaction, written by
  `createContact` itself, not left to a follow-up manual log.** Without
  this, a freshly added contact's tally would start at zero even though
  the very act of adding them records a real meeting — the fact `met_on`/
  `met_at_event_id` already capture on the contact row would be invisible
  in the tally that PRD §4.5 asks for. `logInteraction` therefore never
  accepts `'met'` as a kind; there is exactly one place a `'met'` row is
  written.
- **Tallies are computed live from `interactions`, never a stored counter.**
  This isn't a new call — the table's own migration comment already states
  it as the design ("Tallies (PRD 4.5) are derived from these rows, never
  stored as a counter"); this spec is the first to actually read the table
  that way; recorded here so no later session "optimizes" it into a stored
  count and quietly breaks the append-only guarantee.
- **The compose panel has no LLM component and drafts a fixed template.**
  `docs/ARCHITECTURE.md`'s component table names `invite_suggestion` as the
  place a real, reasoned invite message gets drafted — and that component's
  real prompt is explicitly spec 11's, not built yet. Building a second,
  ad-hoc drafting path here (with or without a model call) would either
  duplicate that future work or ship a worse version of it now. A plain
  template satisfies PRD §4.2's "composed in the CRM" literally.
- **`sms:`/`mailto:` links, not a send API, and a manual confirm afterward.**
  CLAUDE.md's hard rule leaves no other choice for the send half. The
  confirm step is deliberately manual and undetected-by-design: there is no
  way for a web page to know whether the user actually pressed send in the
  native app that just opened, and inventing that certainty (e.g., firing
  the interaction log the instant the link is clicked, before any app
  response) would log an interaction that may not have happened.
- **`logInteraction`'s `kind` is a narrower enum than the column's** (excludes
  `'met'`). This is a schema-level restriction the *action's own input
  validation* enforces, not a database change — `interaction_kind` stays a
  four-value enum matching the migration exactly; only this one write path
  narrows what it accepts.
- **CSV/vCard parsing is hand-rolled, not a new dependency.** Both formats
  are simple, well-documented text grammars — the same call
  `lib/scraping/ics.ts` already made for RFC 5545 — and PRD's own "as far as
  the platform allows" phrasing for phone-contact sync is fully answered by
  a file the user exports once (every mobile Contacts app can share a
  vCard, and CSV is the common spreadsheet fallback) rather than requiring
  a live API no mobile browser exposes to third-party web pages anyway
  (confirmed: no Contact Picker API support relied on here, and the
  Web Share Target API — the mechanism that would let the OS's native
  "Share" sheet hand a file to this PWA directly — is unimplemented on iOS
  Safari as of this writing and untested on this repo's target platforms;
  see Out of scope).
- **An imported contact's `met_on` is left null, never guessed.** The import
  has no real date for when these two people actually met; CLAUDE.md's
  "never invent" rule applies exactly as it did to spec 06's ICS parser
  leaving an unresolvable field null rather than fabricating one.
- **A likely-duplicate import row is flagged, never silently skipped or
  silently merged.** The user decides row by row on the review screen —
  consistent with `CLAUDE.md`'s "never guess, never skip silently" and with
  spec 05's duplicate-names addendum choosing the same shape (surface an
  ambiguity, don't resolve it on the app's own judgment) for a different
  table.
- **Recall/search is a client-side filter, not a new query.** `/people`
  reads every contact once already (there is no pagination need at this
  app's scale, matching every other list page in the app); filtering in the
  browser avoids a redundant round trip for what is, in practice, a small
  personal list.

## Acceptance criteria

- Creating a contact with only a name succeeds and writes exactly one
  `contacts` row and exactly one `interactions` row (`kind: 'met'`) —
  confirmed by reading both tables directly, not inferred from the UI.
- Editing one field on an existing contact (e.g., `notes`) changes only that
  column — every other field, read back afterward, is unchanged.
- Archiving a contact sets `status: 'archived'` via an update; the row still
  exists afterward (no delete ever reaches this table) and appears under the
  page's Archived section with a working Restore control.
- Logging a `'text'`/`'invite'`/`'hangout'` interaction increases that kind's
  tally and the contact's total by exactly one, and a fresh render (after
  the action's own revalidation) shows the new tally — not a stale one, the
  same class of bug specs 04/07/09 each found live once.
- The compose panel's `sms:`/`mailto:` link, inspected directly (its `href`
  attribute, not just "a click does something"), carries the drafted text
  URL-encoded into the `body` parameter. Clicking "I sent this" writes
  exactly one `'text'` interaction — clicking it twice writes two rows (an
  honest log of two confirmations), never zero.
- Importing a vCard file with two valid contacts and one block missing `FN`
  previews exactly two parsed rows plus one warning naming the bad block;
  confirming the import writes exactly two new `contacts` rows (and two
  founding `interactions` rows), read back with the admin client.
- Importing a CSV row whose name matches an existing contact's
  `lower(btrim(name))` is flagged as a likely duplicate on the review
  screen; leaving it unchecked and confirming the rest leaves the existing
  contact's row completely unmodified and inserts nothing for that row.
- The People page's text filter narrows the visible contact list by name,
  phone, email, notes or met-at community/event name with no network
  request (confirm no new request fires while typing).
- Verified per the `CLAUDE.md` rule: `next build` passing is not enough. A
  production server (`next start` or the deployed URL) must serve a real
  authenticated request that renders `/people`, adds a real contact, logs a
  real interaction, and completes a real import — state in `REVIEW.md`
  which of the two verification halves was done, and if the live vCard/CSV
  import step could not be driven through a real browser file input in this
  repo's Playwright setup, say so explicitly rather than implying it was.

## Out of scope

The weekly invite-suggestion job, the real `invite_suggestion` prompt and
model default, and any automatic "who to invite to what" surfacing (PRD
§4.4) — spec 11. Group invites and "N friends going" social proof (PRD
§4.6) — spec 11 or later. The entire viral/k-factor loop from
`docs/specs/10-crm-addition-note.md` (an unauthenticated shareable event
page, one-tap account creation on accept, share-sheet invite scripts) — not
folded in; see Decisions. True native phone-contacts sync via a Contact
Picker API or a registered Web Share Target — neither is reliably available
across this app's target platforms today; file-upload vCard/CSV import is
this spec's answer to "as far as the platform allows." Any LLM-drafted
message — the compose panel's template is fixed text, never a model call.
Editing or deleting an existing interaction row, or a contact's founding
`'met'` row specifically — the log is append-only by design. Any second
user, or sharing a contact list between users.
